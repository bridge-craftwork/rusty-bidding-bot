# Build products and releases

Two products (issue #1):

- **`rbb`**, the command-line tool, for macOS (arm64, x86_64), Linux and
  Windows. Its `bid-pbn` command bids every deal of a PBN file, like
  bba-cli. The rules and the stock cards are compiled in: the binary needs
  nothing beside it.
- **The WASM package** for in-browser bidding: docs/WASM.md.

## `rbb bid-pbn`

```sh
rbb bid-pbn -i deals.pbn -o bid.pbn --ns-card 21GF-DEFAULT.bbsa --ew-card 21GF-GIB.bbsa
```

bba-cli's argument names work too (`--ns-conventions`, `--ew-conventions`),
so a script that calls `bba-cli -i in.pbn -o out.pbn --ns-conventions X.bbsa
--ew-conventions Y.bbsa` calls `rbb bid-pbn` the same way.

| Option | |
|---|---|
| `-i`, `--input` | the PBN file (deals; any auctions in it are replaced) |
| `-o`, `--output` | where to write; `-` for stdout |
| `--ns-card`, `--ew-card` | a `.bbsa` file, card JSON, or a stock card's name (`21GF-DEFAULT`; the list is in `crates/bridge-card/tests/fixtures/bbsa`). `--ew-card` defaults to the North-South card |
| `--set path=value` | a card change for both sides (repeatable), e.g. `general.style=bba` |
| `--scoring MP\|IMP` | for every board, also written as `[Scoring]`; default each board's `[Scoring]`, else MP |
| `--all-meanings` | a note for every call a rule explains, with what it showed (`15-17 HCP, balanced \| 15-17 HCP, 2-5 S, ...`), not only for alerted and announced calls |
| `--auction-prefix "1C Pass 1H"` | force these calls first, then bid |
| `--event NAME` | set `[Event]` |
| `--max-calls N` | stop a runaway auction (default 60); it is finished with `AP` and reported |
| `--rules DIR` | bid with the `.bid` files in DIR instead of the built-in rules |

The output follows bba-cli's layout, so tools that read bba-cli output read
it: a header `% PBN 2.1`, `% Generated by rbb <version>`, `% CC1 - <ns
card>`, `% CC2 - <ew card>` (a previous run's header is replaced, not
stacked); per board `[West/North/East/South "rbb"]`, `[Declarer]`,
`[Contract]` (`3N`, `4SX`; `Pass` with an empty `[Declarer]` when passed
out), `[Auction]` rows with `1N` for notrump, `=n=` note references and four
calls a row, then `[Note "n:text"]`. `[Result]` and `[Score]` are removed
(they described the old contract). Every other tag, comment and `%`
directive of the input is kept byte for byte, so `[DoubleDummyTricks]`,
`[OptimumResultTable]` and the like survive. Deals are bid in parallel; a
500-deal file takes about 0.3 s. A deal that cannot be bid (a hand without
13 cards) loses its auction tags and is reported; the command fails only if
no deal could be bid.

`rbb bid reference` prints the conventions reference (docs/WASM.md,
`reference`).

## Building locally

```sh
cargo build --release -p rbb-cli        # target/release/rbb
crates/wasm/build.sh                    # crates/wasm/pkg/
```

The git dependencies (bridge-types, bridge-encodings, bridge-solver) are
public and pinned in the committed `Cargo.lock`. If you use the local-dev
`[patch]` pattern from bridge-rulebot (a gitignored `.cargo/config.toml`
pointing them at sibling checkouts), keep its `Cargo.lock` changes out of
commits: CI builds with `--locked` against the git pins.

## Releases (GitHub Actions)

- `.github/workflows/ci.yml`: on pushes to main and pull requests, `bid
  check` and `cargo test --workspace` on Linux, macOS and Windows, and the
  WASM package (artifact `rbb-wasm-pkg`).
- `.github/workflows/release.yml`: on a tag `v*` (or run by hand), builds
  `rbb` for `x86_64-unknown-linux-gnu`, `x86_64-pc-windows-msvc`,
  `x86_64-apple-darwin` and `aarch64-apple-darwin`, signs and notarizes the
  macOS binaries, builds the WASM package, and attaches
  `rbb-<os>-<arch>.tar.gz` / `.zip` and `rbb-wasm.tar.gz` to the release.

To release: `git tag v0.1.0 && git push origin v0.1.0`.

### macOS signing and notarization

`scripts/macos-sign.sh <binary>` does it, in the release workflow and by
hand. The same steps and secret names as dealer3's release workflow, so the
same values serve both. The repository needs these five **Actions secrets**
(Settings, Secrets and variables, Actions):

| Secret | What |
|---|---|
| `DEVELOPER_ID_CERT_BASE64` | the **Developer ID Application** certificate with its private key, exported from Keychain Access as `.p12`, then `base64 -i cert.p12` |
| `DEVELOPER_ID_CERT_PASSWORD` | the password chosen when exporting the `.p12` |
| `APPLE_ID` | the Apple ID (email) of a member of the developer team |
| `APPLE_ID_PASSWORD` | an **app-specific password** for that Apple ID (appleid.apple.com, Sign-In and Security), not the account password |
| `APPLE_TEAM_ID` | the ten-character team ID (developer.apple.com, Membership) |

Without them (forks, pull requests) the workflow still builds, and ships
the macOS binaries unsigned, with a notice in the log. With the certificate
but not the Apple ID secrets it signs without notarizing.

The script imports the `.p12` into a temporary keychain, signs with
`codesign --force --options runtime --timestamp --sign "Developer ID
Application"` (hardened runtime, required for notarization), verifies, zips
with `ditto` and submits with `xcrun notarytool submit --wait`. A bare
command-line binary cannot be stapled; Gatekeeper looks the ticket up
online the first time it runs.

By hand, on a Mac whose login keychain has the certificate:

```sh
cargo build --release -p rbb-cli
SIGN_LOCAL=1 APPLE_ID=... APPLE_ID_PASSWORD=... APPLE_TEAM_ID=... \
  scripts/macos-sign.sh target/release/rbb
```
